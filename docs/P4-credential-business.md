# P4 credential business services — 22 October 2026

Owner: abeinoe, assisted by Codex. Scope: private synthetic demo under the existing
G1 exception. This implementation connects the P3 business reservations to real
source-built walt.id issuer, wallet and verifier services. Public deployment,
complete portal/APK journeys and release/operations acceptance retain their P5–P8
gates. Required PR checks must pass before integration.

## Implemented behavior

- Issuer operators create assessments with a persistent, organization-scoped
  candidate/account binding. A candidate or account cannot be reassigned by a new
  assessment. Offer creation is authorized, scoped and idempotent. An atomic
  dispatch reservation prevents concurrent or interrupted retries from issuing
  again. Lost responses stay `RECONCILE_REQUIRED`, including after restart.
- The issuer calls `competencyDemo` / `competency_demo` on the real issuer. Unique
  credential IDs are generated by the issuer. Server-owned explicit NumericDates
  use the actual offer time and an exact 365-day lifetime. The pinned SD-JWT
  handler rounds generated timestamp templates to days/hours; numeric runtime
  overrides deliberately avoid that rounding for this demo requirement.
- Offers returned to operators are authenticated AES-256-GCM encrypted
  `nusacred-offer:` references. They bind the offer, recipient custodial account,
  candidate, original private offer URL and expiry. Share the private 32-byte key
  only between issuer and custodian. No raw preauthorized URL reaches a client.
  The operator obtains the synthetic recipient account ID through the established
  custodial identity flow; arbitrary invented IDs cannot receive the offer.
- The custodian checks the recipient before resolving an offer. It accepts only
  the pinned issuer, configuration and exact token/nonce/credential endpoints.
  Preview does not obtain a token or issue a credential. Explicit consent then
  requests a token, obtains an issuer nonce, signs a proof with the server holder
  key, and fetches with `storeInWallet=true`. It reads the new wallet entry back
  and compares the exact signed credential bytes before reporting completion.
  Receiving reservations are globally unique per offer and survive restart.
- Company sessions snapshot persisted job rules and create real `cross_device`
  requests. DCQL requests all required claim paths with `multiple=true` and no
  competency-value filter. An optional credential ID creates a preview for one
  chosen candidate. Consent binds the original URL, key, selected credential,
  disclosures, recipient, session and access revision. VP tokens remain private.
- Polling first checks result ownership and uses only the stored verifier session
  reference. It requires successful execution of every default SD-JWT VP policy,
  signature, not-before and expiration with `requireField=true`, one query and one
  credential. It validates credential type/vct, every required claim, integer
  NumericDates, validity interval and the public holder-binding shape. Browser
  status or credential claims cannot finalize a result.
- Business decisions use the job snapshot and current trust list in the same
  transaction as the saved trust revision, evaluation time and policy version.
  Competency mismatch, non-competent assessment and untrusted issuer have separate
  reasons. Final rows cannot be overwritten by retries, late responses, trust
  edits, expiry or restart. Dependency outages remain nonfinal; a lost verifier
  session becomes terminal `INCOMPLETE / VERIFIER_SESSION_MISSING`.

The legacy P2 presentation route still previews the first choice for compatibility;
the P4 API returns all available choice labels and accepts an explicit choice.
Complete selection/receiving screens and optical QR/App Link journeys are P5.
Local decline does not claim an upstream cancellation signal. Unknown issuance or
receiving outcomes require operator reconciliation; no automatic resend is added.

## API and migration

`POST /api/v1/exchange-contexts` accepts an encrypted offer reference or an existing
allowlisted presentation request, plus an optional `credentialId` for a selected
presentation. Receiving uses the existing `/{id}/accept` contract with explicit
consent, a matching preview hash, null credential ID and empty disclosures.
Presenting uses `/{id}/present` with the exact selected credential and disclosures.
Offer responses add a nullable `offerUrl`; verification responses add a nullable
`requestUrl`. Errors and limits retain the P3 contract.

Application store schema 2 adds candidate bindings and protocol references.
Migration fails closed if old assessments contain conflicting candidate/account
bindings. Custodian schema 5 adds a unique durable receiving-offer reservation;
wallet/key references and the recovery gate remain unchanged. Back up consistent
application and registry databases before activation. Old binaries reject newer
schemas; rollback requires matching pre-upgrade backups. Do not edit migration
history or start an old binary on an upgraded database.

Issuer startup now requires `OFFER_REFERENCE_KEY_FILE`; custodian receiving is
available only when the same key is mounted. Use the companion infra P4 overlay
and prepare the private key before replacing binaries. The isolated P4 proof
composition adds only loopback diagnostic ports and has no public ingress.

## Validation and reproduction

Ordinary strict builds run all JVM tests, three JVM distributions, Android debug
assembly/lint and production Web/Wasm. No artifact version, repository, reviewed
hash or dependency lock is changed. The workspace P4 validation index records the
exact test totals, scans, source commits and required-check results.

The explicit `:custodian-backend:realBusinessProof` task uses real private fork
services with disposable application databases. It proves receiving/read-back,
controlled retries, unique credential IDs/dates, two eligible competency choices,
matching/mismatching decisions, trust remove/re-add and final-result restart.
Set `P4_PROOF_RUNTIME` to a fresh ignored runtime path and `P4_PORT_BASE=27000` for
the isolated P4 stack (default 17000 for the accepted P2 diagnostics).

The infra negative runner issues fixtures through the real issuer, then submits
controlled holder-bound SD-JWT responses. `:backend-common:realPolicyProof` reads
those private verifier responses and exercises the application policy/decision
adapter. Set `P4_NEGATIVE_RUNTIME` to that runner's output directory. Some malformed
NumericDates are rejected by the issuer before a signed fixture exists; the
report identifies that layer explicitly. Unit tests independently cover each
missing/wrong-type required claim, including `iss` and `cnf`, every required VP
policy, NumericDate types, recipient/expiry/tamper, candidate rebinding, ambiguous
dispatch, missing verifier session, cross-account polling and immutable decisions.
Never describe issuer refusal as verifier rejection or a wallet-filtered case as
an end-to-end business rejection.

The infrastructure continuity runner reloads a supported profile on the isolated
issuer, preserves identity/key material, compares old credential bytes and proves
successful real verification after restart. `did:jwk` embeds the retained public
verification key; private key rotation is intentionally unsupported in this demo.
Off-host encrypted backup and restoration remain P7 requirements.
